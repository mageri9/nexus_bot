# 📡 Nexus (v0.3)

> **Nexus** — это событийно-ориентированное ядро управления (Control Plane), мониторинга и автоматической ИИ-диагностики (AIOps) для экосистемы Telegram-ботов и микросервисов на вашем сервере.

Система разделена на независимые слабосвязанные слои, работает по паттерну DooD (Docker-out-of-Docker) и использует Redis в качестве шины Pub/Sub и кэша состояний, обеспечивая нулевое влияние на производительность хоста во время сборки и мгновенный отклик интерфейса.

---

## 🏗️ Архитектура системы (Nexus Control Plane)

```text
                  GitHub Actions (CI/CD)
                            │
                            ▼ (HTTP POST Webhook, подпись HMAC-SHA256)
               ┌───────────────────────────┐
               │    nexus-webhook (8000)   │ (FastAPI)
               └────────────┬──────────────┘
                            │ (redis_client.publish)
                            ▼
                    [ Redis Pub/Sub ] <--- (Внешние события)
                            │
                            ▼ (pubsub_listener.py)
       Telegram <────── EventBus ───────── IncidentService <─── StateCollector (Bg Ticker)
   (Persistent Menu)  (pub/sub inside)    (Redis History)               │ (Каждые 5 сек)
                                                                        ▼
                                                                  Project Agents
                                                               (imagebot, tarot...)
                                                                        │
                                                          docker-socket-proxy (whitelist API)
                                                                        │
                                                                 Docker Daemon (хост)
                                                                 Disk Host Mount (per-project, ro)
```

### Ключевые компоненты:

1. **DooD через изолированный прокси (не прямой сокет):** Ядро Nexus не монтирует `/var/run/docker.sock` напрямую. Вместо этого сокет виден только сервису `docker-socket-proxy` (изолирован во внутренней Docker-сети без выхода наружу), который отдаёт наружу whitelist конкретных методов Docker API (`inspect`, `stats`, `logs`, `restart`) и явно запрещает опасные (`exec`, `build`, `commit`, управление образами/volume). Компрометация процесса Nexus сама по себе больше не эквивалентна root-доступу на хосте.
2. **State Change Detection (Event Sourcing-lite):** Сборщик состояний `StateCollector` опрашивает контейнеры раз в 5 секунд. Он сверяет новые метрики с кэшем в Redis и генерирует точечные события изменения состояния (`ResourceStopped`, `ResourceRecovered` и др.) в `EventBus` только при реальных изменениях. Это полностью решает проблему спама алертами.
3. **Incident Service:** Автоматическая служба ведения инцидентов. При сбое ресурса заводится инцидент со сквозным номером (например, `#42`), фиксируется точный счетчик рестартов, время открытия и слепок последних логов. Открытие инцидента защищено атомарной блокировкой (`SET NX` с TTL 1 час) — повторные события отказа для того же ресурса не создают дублирующихся инцидентов, даже при гонке между несколькими почти одновременными событиями. При восстановлении инцидент автоматически закрывается с подсчетом времени простоя.
4. **Auto-AI Diagnostics (Gemma 4):** В момент аварии Nexus мгновенно высылает карточку инцидента в Telegram, а в фоне асинхронно отправляет логи сбоя в модель Gemma 4 через шлюз AITUNNEL. Готовый технический диагноз и план устранения приходят в виде Reply-ответа к исходному алерту. Объём логов, передаваемых модели, ограничен бюджетом символов и числом ресурсов на запрос — каскадное падение нескольких сервисов сразу не приводит к неконтролируемому росту промпта.
5. **Decoupled Webhook Receiver & Redis Pub/Sub:** Для интеграции с CI/CD (GitHub Actions) выделен независимый микросервис на FastAPI. Он принимает входящий HTTP-трафик из внешнего мира, проверяет подлинность запроса по HMAC-подписи (`X-Hub-Signature-256`), сериализует его в плоские события и публикует в Redis Pub/Sub, откуда бот забирает их в фоновом потоке. Бот не блокируется обработкой сетевого трафика.
6. **Cloudflare Quick Tunnel:** Позволяет принимать входящие вебхуки от GitHub Actions по HTTPS-каналу на сервере без домена и статического IP. Поскольку Quick Tunnel выдаёт новый случайный поддомен при каждом рестарте, адрес вебхука в GitHub синхронизируется автоматически: сайдкар-процесс парсит новый URL из логов `cloudflared` и обновляет его через GitHub API.

## 🔒 Модель безопасности

* **Доступ к боту:** все хэндлеры сообщений и все callback-кнопки (restart, silence, AI diagnose) защищены фильтром `IsAdmin`, привязанным к списку `ADMIN_IDS`. Проверка применена как к `message`, так и к `callback_query` роутерам.
* **Webhook:** входящие запросы от GitHub принимаются только с валидной HMAC-SHA256 подписью, посчитанной по `GITHUB_WEBHOOK_SECRET`. Запросы без подписи или с неверной подписью отклоняются с `401` до какой-либо обработки.
* **Docker API:** доступ к Docker daemon хоста идёт не напрямую через сокет, а через `docker-socket-proxy` с ограниченным набором разрешённых методов. `docker exec` и управление образами через прокси недоступны в принципе.
* **Дисковые точки монтирования:** каждому проекту доступен на чтение только его собственный каталог данных (`:ro`), а не файловая система хоста целиком — за исключением служебного мониторинга системного диска (`root_disk` в самом Nexus), которому по смыслу задачи нужен весь `/`.

## 📊 Математика расчета Health Score (0 - 100%)

Вместо случайных значений здоровье каждого проекта вычисляется динамически на основе весовых штрафов за сбои ресурсов и перегрузку:
* **Стартовый баланс:** `100` баллов.
* **Сбой ресурса (status != running/healthy):** `-50` баллов за каждый упавший компонент.
* **Критическая утилизация CPU (>95%):** `-15` баллов.
* **Критическая утилизация RAM (>90%):** `-15` баллов.
* **Каждый перезапуск контейнера (RestartCount):** `-5` баллов.
* **Сбой критических СУБД (redis, postgres):** Дополнительный штраф `-20` баллов.

## 📡 Команды управления терминалом

Администрирование полностью защищено фильтром `IsAdmin` (на сообщениях и на callback-кнопках) и доступно только пользователям из списка `ADMIN_IDS`:

* `/start` — Инициализирует сессию и закрепляет внизу экрана постоянную кнопку **📡 Status** (Reply Keyboard).
* **📡 Status** (или `/status`) — Выводит детальный ASCII/HTML-отчет о здоровье всей фермы проектов, утилизации CPU/RAM, объеме дисков и рестартах. Снабжается интерактивными инлайн-кнопками ручного перезапуска контейнеров.
* **Инлайн-действия в алерте инцидента:**
    * `🔄 Restart` — Попытка ручного перезапуска сбойного контейнера.
    * `📝 Logs` — Запрос свежего слепка логов (до 40 строк).
    * `🧠 AI Diagnose` — Повторный ручной вызов ИИ-диагностики логов.
    * `🔕 Silence 1h` — Включает режим тишины в Redis для этого ресурса на 1 час (блокирует повторную отправку алертов при циклическом падении контейнера).

## 🛠️ Расширение системы

Добавление нового бота на сервере в систему мониторинга Nexus занимает 1 минуту:

1. Опишите ресурсы нового бота в `agents/manifest.py`:
   ```python
   my_new_bot = ProjectAgent(
       name="my_new_bot",
       resources={
           "app": DockerContainer("app", local_transport, "my-bot-container"),
           "postgres": DockerContainer("postgres", local_transport, "my-postgres-container"),
           "data_disk": DiskResource("data_disk", local_transport, "/host_root/home/mageri9/apps/my_bot/data")
       }
   )
   ```
2. Зарегистрируйте его в `agents/__init__.py`:
   ```python
   registry.register(my_new_bot)
   ```
3. Если у нового проекта есть собственный каталог данных на хосте — добавьте точечный `:ro`-маунт под этот путь в `docker-compose.yml` (сервис `nexus`), не расширяя доступ шире необходимого.

Система автоматически начнет собирать его метрики утилизации ресурсов, отображать реальное дисковое пространство хоста, вычислять Health Score и отправлять ИИ-аналитику в случае аварийных падений.

## ⚙️ Конфигурация (`.env`)

| Переменная | Назначение |
|---|---|
| `BOT_TOKEN` | Токен Telegram-бота |
| `REDIS_URL` | Строка подключения к Redis |
| `ADMIN_IDS` | Список Telegram ID администраторов через запятую |
| `AITUNNEL_API_KEY` | Ключ шлюза AITUNNEL для доступа к модели Gemma 4 |
| `GITHUB_WEBHOOK_SECRET` | Секрет для проверки HMAC-подписи входящих GitHub-вебхуков |
| `GITHUB_TOKEN` | (опционально) PAT с правом управления вебхуками — используется сайдкаром синхронизации URL туннеля |
| `GITHUB_REPO` | (опционально) `owner/repo`, вебхук которого нужно синхронизировать |

## 📌 Известные ограничения

* Без собственного домена туннель работает через Cloudflare Quick Tunnel — адрес нестабилен между рестартами; синхронизация с GitHub автоматическая, но в момент смены URL возможна кратковременная потеря CI/CD-уведомления (не влияет на основной мониторинг инфраструктуры).
* Автотесты пока отсутствуют — логика детекции переходов состояний и дедупликации инцидентов проверялась вручную и ревью кода.

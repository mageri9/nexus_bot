# 📡 Nexus (v2.0)

> **Nexus** — это событийно-ориентированная платформа управления (Control Plane), непрерывного наблюдения (Observability) и динамического выявления аномалий и скрытых угроз (AIOps) для экосистемы Telegram-ботов и микросервисов на вашем VPS.

Система разделена на изолированные слои, работает по паттерну DooD (Docker-out-of-Docker) через безопасный сокет-прокси и использует Redis в качестве оперативной шины Pub/Sub, а SQLite — для неблокирующей долгосрочной аналитической памяти и обучения ИИ-моделей.

## 🧠 Интеллектуальный слой (Intelligence Engine v2.0)

В версии 2.0 Nexus получил развитый встроенный слой ИИ-аналитики и машинного обучения (AIOps), развернутый локально на вашем VPS без привлечения тяжелых сторонних SaaS-платформ.

### 1. Долговременная SRE-память (SQLite WAL)
Система оснащена неблокирующей базой данных `data/events.db` в режиме транзакционного логирования (WAL). Операции записи изолированы в фоновых потоках через `asyncio.to_thread`, что гарантирует нулевое влияние дискового ввода-вывода на реакцию основного управляющего интерфейса.
* **Таблица `event_log`:** Содержит полную хронологию размеченных событий, прошедших классификацию, дедупликацию и разметку критичности (`severity`).
* **Таблица `metric_snapshots`:** Каждые 5 секунд сохраняет числовые срезы производительности (`CPU`, `RAM`, рестарты, сетевой статус) по каждому ресурсу для последующего анализа и обучения моделей.

### 2. Статистический анализатор аномалий (Z-Score)
Вместо фиксированных лимитов (вроде «алерт при RAM > 90%») Nexus выявляет динамические аномалии с помощью метода скользящего Z-score (метод трех сигм) на чистом Python:
* Сборщик анализирует историю поведения конкретного контейнера за последние 10 минут (до 120 точек).
* Рассчитывается динамическое среднее и стандартное отклонение (уровень фонового шума ресурса).
* Если текущее значение отклоняется от исторической нормы более чем на 3 стандартных отклонения (Z-score > 3.0), генерируется и записывается событие `ml:anomaly_detected`, а администраторам в Telegram уходит карточка предупреждения.
* **Защита от ложного шума:** Если стандартное отклонение стремится к нулю (показатель абсолютно стабилен), проверка принудительно блокируется, исключая ложные тревоги при изменении нагрузки на доли процента.

### 3. Предиктивный ИИ-анализ (CatBoost Classifier)
Архитектура предиктивного анализа построена на базе единого интерфейса `MLTask` и первой специализированной задачи `IncidentPredictionTask`.
* **Автоматическая разметка (Target):** Каждая строчка метрик размечается единицей (`target = 1`), если в течение следующих 30 минут по этому же ресурсу открылся реальный инцидент (зафиксировано падение или деградация), и нулем (`target = 0`), если работа продолжилась стабильно.
* **Прослеживаемость (Traceability):** Каждая строка датасета сохраняет ссылку на `event_id` (ID снимка метрик), позволяя ИИ-диагносту ретроспективно объяснить логику предсказания.

### 4. Baseline-гейт (Дискрепанс-шлюз)
Для предотвращения выгорания от уведомлений (Alert Fatigue) в ядро интегрирован шлюз сопоставления рисков:
* Предиктор рассчитывает вероятность сбоя по модели ИИ (`ml_risk` от `0.0` до `1.0`).
* Традиционные правила `HealthEngine` переводят текущее здоровье бота в базовый риск (`engine_risk` от `0.0` до `1.0`).
* Оповещение об угрозе отправляется в Telegram **только в случае критического расхождения**: если ИИ видит скрытую угрозу (например, плавную утечку памяти, `ml_risk > 0.6`), а традиционные правила все еще считают здоровье равным 100% (`engine_risk = 0.0`), так как жесткие пороговые лимиты формально еще не превышены.

### 5. Локальный реестр моделей и контроль версий
Обучение выполняется изолированно через cron-скрипт `scripts/train.py`. Версии моделей и метрики качества на проверочной (holdout) выборке фиксируются в файле `models/incident_prediction_registry.json`.
* Модели разделяются по времени (train на прошлом, holdout на последних 20% хронологической истории).
* Оценка выполняется по метрике площади под кривой точности-полноты (**PR-AUC**), что идеально подходит для редких SRE-событий с сильным дисбалансом классов.
* **Защита от деградации:** Новая модель записывается на диск и принимается ядром в качестве основной только в том случае, если её метрика PR-AUC на holdout-выборке не хуже предыдущей.

## 🎛️ Наблюдаемость и классические функции ядра

1. **Непрерывный стриминг логов (Log Ring Buffer):** Фоновая служба `LogCollector` постоянно слушает вывод контейнеров через `docker logs -f` и пишет их в списки Redis с автоматическим усечением (последние 100 строк). Это гарантирует мгновенный доступ к логам для UI-интерфейса и AI-диагностики, сохраняя контекст непосредственно перед падением.
2. **Многофреймворковый `nexus_sdk`:** Готовый легковесный пакет для интеграции наблюдаемости в ваших ботов. Нативно поддерживает как **`aiogram`**, так и **`python-telegram-bot`** (PTB).
3. **Виртуальный пульс (Heartbeat):** Бот через SDK шлет сигналы `app:heartbeat` каждые 15 секунд. Виртуальный ресурс `ApplicationHeartbeat` в ядре проверяет время затухания пульса в Redis. Если бот зависнет или отключится, система зафиксирует это как `unhealthy` и заведет инцидент — класс отказов, недостижимый через обычную проверку статуса контейнера.
4. **Унифицированный классификатор сигналов (`Classifier`):** Промежуточный слой, преобразующий любые события (сбои контейнеров, DevOps-деплои, ошибки приложений из SDK) в единый формат `Signal`. Централизует проверку режима техобслуживания, определение уровней критичности (`HIGH`, `MEDIUM`, `INFO` и т.д.) и подавление ложных срабатываний.
5. **Реестр ошибок и дедупликация (Error Registry):** При получении трейсбэка ошибки из SDK система отсекает служебные фреймы фреймворков и вычисляет уникальный `fingerprint` ошибки (на основе первого non-framework фрейма). Ошибка логируется в хэш-таблицу в Redis с увеличением счётчика повторений, фиксацией времени активности и статуса.
6. **Авто-восстановление приложений (Auto-Recovery):** Если инцидент уровня приложения (`app:error`) открыт, но повторные ошибки с этим fingerprint не фиксируются в течение определенного времени, коллектор автоматически закрывает инцидент с фиксацией общего времени простоя.
7. **Подавление шума при деплоях:** CI/CD-пайплайн перед пересозданием контейнеров сам выставляет временный флаг `nexus:maintenance:{agent}` в Redis. Пока он активен, `Classifier` не пропускает сигналы о сбоях этого агента — ожидаемый флап контейнера при деплое не порождает ложный инцидент. Дополнительно `StateCollector` требует несколько подряд идущих подтверждений нового статуса, прежде чем он коммитится (дебаунс).

## 💻 Интеграция `nexus_sdk` в ваших ботов

Интеграция занимает несколько строк в файле инициализации или запуска вашего бота.

### Вариант А. Бот на фреймворке `aiogram` (v3)
```python
import asyncio
from aiogram import Bot, Dispatcher
from nexus_sdk import NexusSDK

bot = Bot(token="TOKEN")
dp = Dispatcher()

# Инициализируем SDK
nexus = NexusSDK(
    endpoint_url="http://nexus-webhook:8000/events/app",
    app_secret="ТВОЙ_NEXUS_APP_SECRET",
    project_name="my_aiogram_bot"  # Строго совпадает с именем агента в манифестах Nexus
)

# 1. Подключаем глобальный перехватчик ошибок
nexus.register_aiogram_error_handler(dp)

# 2. Запускаем периодическую отправку пульса (Heartbeat) раз в 15 секунд
nexus.start_heartbeat(interval_seconds=15)

async def main():
    try:
        await dp.start_polling(bot)
    finally:
        await nexus.close()  # Грациозно останавливаем сессию SDK при остановке бота

if __name__ == "__main__":
    asyncio.run(main())
```

## 🔒 Модель безопасности

* **Фильтрация доступа:** Все управляющие команды, а также интерактивные inline-действия (Restart, Logs, AI Diagnose, Silence) защищены фильтром `IsAdmin` на уровне сообщений и callback-запросов.
* **Безопасность Webhook-приёмника:** Все входящие запросы принимаются только при наличии валидной HMAC-SHA256 подписи в заголовках. Для GitHub-вебхуков используется `GITHUB_WEBHOOK_SECRET`, для приложений-клиентов через SDK — `NEXUS_APP_SECRET`. Отсутствие подписи или несовпадение ключа прерывают обработку на раннем этапе (fail-closed).
* **Сетевая изоляция:** Сервис вебхуков принимает входящие сигналы от ботов исключительно внутри приватной Docker-сети `nexus_shared` на хосте VPS, не открывая порты во внешний мир.
* **Docker API Proxy:** Доступ к сокету Docker идет не напрямую, а через `docker-socket-proxy` с ограниченным набором методов. `docker exec` и удаление образов заблокированы на сетевом уровне сокета.

## 📊 Математика расчёта Health Score (0–100%)

Показатель здоровья агента рассчитывается динамически на каждом тике:
* **Стартовый баланс:** `100` баллов.
* **Сбой ресурса** (`status != running/healthy`): `-50` баллов за каждый упавший компонент.
* **Критическая утилизация CPU** (>95%): `-15` баллов.
* **Критическая утилизация RAM** (>90%): `-15` баллов.
* **Каждый перезапуск контейнера** (`RestartCount`): `-5` баллов.
* **Сбой критических СУБД** (redis, postgres): дополнительный штраф `-20` баллов.

## 🛠️ Запуск аналитических инструментов на VPS

Благодаря контейнеризации, вам не нужно устанавливать Python, Pandas или CatBoost на сам хост-сервер. Все инструменты запускаются напрямую внутри контейнера `nexus-core`.

### 1. Ручной запуск и тестирование обучения моделей
Вы можете принудительно запустить ночной цикл обучения моделей прямо сейчас:
```bash
docker exec -it nexus-core python scripts/train.py incident_prediction
```
*Скрипт выгрузит историю снимков из SQLite, разобьет её по времени, проверит качество PR-AUC на holdout-выборке и запишет новую версию в модельный реестр на диске.*

### 2. Запуск авто-обучения по расписанию (cron)
Чтобы модель регулярно переобучалась на свежих метриках, добавьте задачу в планировщик задач хост-сервера (`crontab -e`):
```text
0 3 * * * docker exec nexus-core python scripts/train.py incident_prediction >> /home/mageri9/apps/nexus/train_cron.log 2>&1
```
*Обучение будет запускаться каждую ночь в 03:00, сохраняя логи в текстовый отчет.*

### 3. Запуск SRE-консоли офлайн-анализа
Вы можете мгновенно проанализировать накопленную историю логов и метрик, выполнив SRE-скрипт аналитики:
```bash
docker exec -it nexus-core python scripts/explore.py
```
*Консоль выведет:*
* *Суммарное количество инцидентов по всем проектам.*
* *Топ падающих и нестабильных ресурсов.*
* *Детальную корреляцию падений ресурсов сразу после деплоев с GitHub (в пределах 30 минут).*
* *Все критические предупреждения в экосистеме за последние 24 часа.*

# 📡 Nexus (v0.3)

> **Nexus** — событийно-ориентированное ядро управления (Control Plane), мониторинга и автоматической ИИ-диагностики (AIOps) для экосистемы Telegram-ботов и микросервисов на вашем VPS.

Система разделена на независимые слабосвязанные слои, работает по паттерну DooD (Docker-out-of-Docker) и использует Redis в качестве шины Pub/Sub и кэша состояний, обеспечивая нулевое влияние на производительность хоста и мгновенный отклик интерфейса.

### Ключевые компоненты

1. **DooD через изолированный прокси (не прямой сокет).** Ядро Nexus не монтирует `/var/run/docker.sock` напрямую. Сокет виден только `docker-socket-proxy` (изолирован во внутренней сети без выхода наружу), который отдаёт наружу whitelist методов Docker API (`inspect`, `stats`, `logs`, `restart`) и явно запрещает опасные (`exec`, `build`, `commit`, работу с образами/volume). Компрометация процесса Nexus не эквивалентна root-доступу на хосте.
2. **State Change Detection (Event Sourcing-lite).** `StateCollector` опрашивает ресурсы раз в 5 секунд, сверяет с кэшем в Redis и публикует в `EventBus` точечные события (`ResourceStopped`, `ResourceRecovered` и др.) только при реальных изменениях статуса — без спама одинаковыми алертами.
3. **Incident Service.** При сбое заводится инцидент со сквозным номером, фиксируется счётчик рестартов, время открытия и слепок логов. Открытие защищено атомарной блокировкой `SET NX` в Redis — повторные события отказа того же ресурса не плодят дубликаты, даже при гонке между почти одновременными событиями. При восстановлении лок снимается явным `DELETE`, инцидент закрывается с подсчётом времени простоя.
4. **Auto-AI Diagnostics.** В момент аварии карточка инцидента мгновенно уходит в Telegram, а в фоне логи асинхронно уходят в модель через шлюз AITUNNEL. Диагноз и план устранения приходят Reply-ответом на исходный алерт. Объём логов, передаваемых модели, ограничен бюджетом символов и числом ресурсов на запрос — каскадное падение нескольких сервисов не приводит к неконтролируемому росту промпта.
5. **Decoupled Webhook Receiver & Redis Pub/Sub.** Для CI/CD выделен независимый FastAPI-сервис. Он проверяет подлинность запроса по HMAC-подписи (`X-Hub-Signature-256`), публикует событие в Redis Pub/Sub, откуда бот забирает его фоново — не блокируясь обработкой сетевого трафика.
6. **Cloudflare Quick Tunnel.** Принимает вебхуки от GitHub Actions по HTTPS без домена и статического IP. При каждом рестарте выдаётся новый поддомен — сайдкар парсит URL из логов `cloudflared` и обновляет его через GitHub API автоматически.

## 🔒 Модель безопасности

* **Доступ к боту:** все хэндлеры сообщений и все callback-кнопки (restart, silence, AI diagnose) защищены фильтром `IsAdmin`, привязанным к списку `ADMIN_IDS` — как для `message`, так и для `callback_query`.
* **Webhook:** входящие запросы принимаются только с валидной HMAC-SHA256 подписью. Если `GITHUB_WEBHOOK_SECRET` не задан или подпись неверна — запрос отклоняется с `401` до какой-либо обработки (fail-closed, а не fail-open).
* **Docker API:** доступ идёт не напрямую через сокет, а через `docker-socket-proxy` с ограниченным набором методов. `docker exec` и управление образами через прокси недоступны в принципе.
* **Дисковые точки монтирования:** каждому проекту доступен на чтение только его собственный каталог данных (`:ro`), кроме служебного `root_disk` у самого Nexus, которому по смыслу задачи нужен весь `/` (осознанный компромисс, а не оплошность).

## 📊 Математика Health Score (0–100%)

Здоровье проекта вычисляется динамически на основе весовых штрафов:

* **Стартовый баланс:** `100` баллов.
* **Сбой ресурса** (`status != running/healthy`): `-50` баллов за каждый упавший компонент.
* **Критическая утилизация CPU** (>95%): `-15` баллов.
* **Критическая утилизация RAM** (>90%): `-15` баллов.
* **Каждый перезапуск контейнера** (`RestartCount`): `-5` баллов.
* **Сбой критических СУБД** (redis, postgres): дополнительный `-20` баллов.

## 📡 Команды управления терминалом

Всё администрирование защищено фильтром `IsAdmin` и доступно только пользователям из `ADMIN_IDS`:

* `/start` — инициализирует сессию, закрепляет кнопку **📡 Status**.
* **📡 Status** (или `/status`) — детальный отчёт о здоровье всей фермы проектов, утилизации CPU/RAM, объёме дисков и рестартах, с инлайн-кнопками перезапуска.
* **Инлайн-действия в карточке инцидента:**
    * `🔄 Restart` — ручной перезапуск сбойного контейнера.
    * `📝 Logs` — свежий слепок логов (до 40 строк).
    * `🧠 AI Diagnose` — повторный ручной вызов ИИ-диагностики.
    * `🔕 Silence 1h` — режим тишины в Redis на 1 час (защита от спама при циклическом падении контейнера).

## 🛠️ Расширение системы

1. Опишите ресурсы нового бота в `agents/manifest.py`:
   ```python
   my_new_bot = ProjectAgent(
       name="my_new_bot",
       resources={
           "app": DockerContainer("app", local_transport, "my-bot-container"),
           "postgres": DockerContainer("postgres", local_transport, "my-postgres-container"),
           "data_disk": ProjectStorageResource("data_disk", local_transport, "/host_root/home/.../my_bot/data")
       }
   )
   ```
2. Зарегистрируйте его в `agents/__init__.py`: `registry.register(my_new_bot)`.
3. Добавьте точечный `:ro`-маунт под каталог данных нового проекта в сервис `nexus` в `docker-compose.yml`, не расширяя доступ шире необходимого.

Система автоматически начнёт собирать метрики, отображать реальное дисковое пространство, вычислять Health Score и присылать ИИ-аналитику при авариях.

## 📌 Известные ограничения и рекомендации

* **Блокировка инцидента не имеет TTL.** `IncidentService.on_resource_failed` ставит лок через `SET NX` без `EX`. Он корректно снимается через `DELETE` при штатном событии `ResourceRecovered`, но если ресурс исчезнет из манифеста (переименован/удалён) вместо восстановления, придёт `ResourceDeleted`, на который сервис не подписан — лок останется навсегда, и при повторном появлении ресурса под тем же именем новые инциденты создаваться не будут. **Рекомендация:** добавить `ex=3600` к `SET NX` как страховочный TTL и/или подписать `IncidentService` на `ResourceDeleted`.
* **`StateCollector._loop`** оборачивает обход всех агентов в один `try/except` — необработанное исключение на одном ресурсе прерывает обновление всех остальных агентов до следующего тика. Рекомендуется изолировать обработку каждого агента отдельным `try`.
* **`QueryService.get_system_status`** в ветке legacy V1-данных обращается к `res_data["status"]` без `.get()` — при повреждённом старом слепке в Redis возможен `KeyError`.
* Без собственного домена туннель работает через Cloudflare Quick Tunnel — адрес нестабилен между рестартами; синхронизация с GitHub автоматическая, но в момент смены URL возможна кратковременная потеря CI/CD-уведомления (не влияет на основной мониторинг инфраструктуры).
* Автотесты пока отсутствуют — логика детекции переходов состояний и дедупликации инцидентов проверялась вручную и код-ревью.


# Тесты для Nexus

Готовый набор unit-тестов для `core/`, `infra/`, `services/` (кроме `ai.py`,
завязанного на внешний AITUNNEL API) и `webhook_service.py`. Всего **100
тестов**, все проходят на текущей версии кода из репозитория.

## Установка

Скопируйте `tests/` и `pytest.ini` в корень репозитория Nexus (рядом с `main.py`),
затем:

```bash
pip install -r requirements-dev.txt --break-system-packages   # или в venv без флага
pytest
```

Тесты **не требуют** ни реального Redis, ни Docker, ни сети — везде, где код
обращается к Redis, подставляется `fakeredis.FakeAsyncRedis` (in-memory,
изолированный на каждый тест), а вместо `LocalShellTransport` — управляемый
`ScriptedTransport` из `conftest.py`, который отвечает по заранее заданному
сценарию.

`telegram/` и `services/ai.py` намеренно не покрыты: первое — это в основном
проводка aiogram-хендлеров с минимумом собственной логики, второе требует
реального (или сложно мокаемого) OpenAI-совместимого клиента. Их можно
добавить отдельно при необходимости.

## ⚠️ Два теста специально фиксируют текущие баги, а не ожидаемое поведение

Они помечены суффиксом `_KNOWN_BUG` и снабжены подробным docstring:

1. **`test_incident_service.py::test_active_incident_lock_has_no_ttl_KNOWN_BUG`**
   Блокировка активного инцидента (`SET NX`) ставится без `ex=3600`, хотя
   комментарий в коде и README утверждают обратное. Тест проверяет, что TTL
   ключа равен `-1` (не установлен). Если это поправят — тест начнёт падать,
   и его нужно инвертировать/удалить.

2. **`test_collector.py::test_custom_other_category_resource_transitions_are_never_tracked_KNOWN_BUG`**
   Найден в процессе написания этого набора тестов: `StateCollector`
   раскладывает ресурсы по `containers`/`storage`/`other`, но при
   восстановлении предыдущего состояния (`old_resources_statuses`) читает
   только `containers` и `storage` — категория `other` игнорируется. Любой
   кастомный `Resource` (не `DockerContainer`/`HostDiskResource`/
   `ProjectStorageResource`) будет считаться "впервые увиденным" на **каждом**
   тике: события `ResourceStopped`/`ResourceRecovered`/`ResourceDeleted` для
   него никогда не сработают, а `ResourceStarted`/`ResourceUnhealthy` будут
   публиковаться повторно каждые `interval` секунд. Сейчас в
   `agents/manifest.py` кастомных типов нет, поэтому баг спит — но
   "выстрелит" при добавлении нового типа ресурса, для чего явно оставлен
   фолбек в `core/resource.py` и `services/collector.py`.

Оба бага не выдуманы под тест — оба воспроизводятся на реальном коде из
предоставленного репозитория.
